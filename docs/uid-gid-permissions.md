# UID, GID and permissions

## Что такое UID/GID
В Linux у каждого файла есть числовой владелец — UID (user id) и группа — GID (group id).
Ядро проверяет права доступа по этим числам, а не по имени пользователя.
Имя (например, sultan или www-data) — это лишь удобная подпись; одно и то же число
в разных окружениях может показываться под разными именами или вообще без имени.

## Почему root-owned files ломают dev workflow
Контейнер запускает процесс под каким-то UID. Если это UID 0 (root) и контейнер
пишет файлы в bind mount (./:/var/www/html), файлы появляются на host с владельцем root.
Обычный пользователь (например, UID 1000) не может их удалить или изменить без sudo.
Получается цикл: контейнер пишет как root -> host не может редактировать -> человек
делает sudo chmod -> права становятся шире -> причина остаётся.

## Как узнать id -u и id -g
На host выполнить:
- `id -u` — мой UID (обычно 1000)
- `id -g` — мой GID
- `id` — всё сразу
Эти числа кладутся в .env (APP_UID, APP_GID), чтобы контейнер с
`user: "${APP_UID}:${APP_GID}"` писал файлы под моим пользователем.

## Чем Linux отличается от macOS / Windows / WSL2
- Linux: ownership виден напрямую, root-owned файлы — реальная проблема.
- macOS / Windows: Docker Desktop работает через виртуальную машину и слой синхронизации
  файлов, поэтому ownership проявляется иначе. Проблемы могут выглядеть как медленная
  работа, file watcher issues, странные ограничения записи.
- Windows/WSL2: проект лучше держать внутри Linux filesystem WSL (~/projects/...),
  а не в /mnt/c/..., чтобы права/скорость были ближе к Linux-модели.

Моя ОС: macOS (Docker Desktop через VM). Поэтому root-owned проблема может не
воспроизводиться так, как на чистом Linux. Но контракт APP_UID/APP_GID всё равно нужен —
для команды и для Linux-машин, где это критично.

## Почему chmod -R 777 не является нормальным решением
chmod -R 777 даёт чтение, запись и выполнение всем пользователям. Это слишком широкий
доступ, а рекурсивно по всему проекту он меняет security-модель кода, секретов и скриптов
без разбора. Главное — он не лечит причину: контейнер по-прежнему пишет как root, поэтому
новые файлы снова появятся root-owned. Правильное решение — запускать процесс под нужным
UID/GID через `user: "${APP_UID}:${APP_GID}"`, тогда файлы сразу создаются с владельцем,
которым host может управлять.
