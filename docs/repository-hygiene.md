# Repository hygiene

Принцип: Git хранит source of truth и contract проекта, а локальное
состояние компьютера живёт вне истории. Чистый репозиторий делает review
тихим, diff маленьким, backport простым, а release — надёжным.

## Что МОЖНО commit-ить

Это то, что нужно, чтобы воспроизвести проект и понять решения команды:

- Source code — основной код проекта.
- Tests — тесты, проверяющие поведение.
- Docs — документация (включая этот файл).
- Makefile — повторяемые команды проверки и сборки.
- `.env.example` — список нужных переменных без реальных значений,
  чтобы новый разработчик знал, что настроить.
- CHANGELOG.md — отредактированная история изменений по версиям.
- Release notes — коммуникация по конкретному выпуску.
- Migrations и config examples — то, что определяет contract проекта.

## Что НЕЛЬЗЯ commit-ить

Это локальное и воспроизводимое состояние, которому не место в истории:

- Real secrets — настоящие ключи, токены, пароли. Это security-риск.
- Local `.env` — реальные переменные окружения конкретной машины.
- Logs — файлы логов (*.log), меняются постоянно и бесполезны в истории.
- Cache — кэш и временные данные.
- Generated artifacts без явной причины — build output, coverage-отчёты,
  скачанные зависимости (vendor/, node_modules/). Если это можно получить
  командой — хранить в Git не нужно.

Правило не "игнорировать всё с точкой", а "не хранить личное и
воспроизводимое".

Если generated artifact всё же нужен в репозитории, команда обязана явно
описать: почему он versioned, кто его обновляет и как проверяет.

## Already tracked files и git rm --cached

`.gitignore` влияет только на untracked файлы — он подсказывает Git не
предлагать к добавлению то, что ещё не отслеживается. Если файл уже tracked
(уже в index), правило в `.gitignore` его НЕ уберёт: Git знает его path и
продолжит показывать изменения.
