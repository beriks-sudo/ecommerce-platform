git@github.com:beriks-sudo/ecommerce-platform.git
https://github.com/beriks-sudo/ecommerce-platform.git

Один и тот же репозиторий доступен по двум протоколам, и это два разных remote URL для одного места:

HTTPS: https://github.com/<username>/ecommerce-platform.git
SSH: git@github.com:<username>/ecommerce-platform.git

Это один репозиторий на серверах GitHub — меняется только транспорт. HTTPS аутентифицируется через токен/учётные данные поверх HTTP, а SSH — через пару ключей по SSH-протоколу. Выбор формата влияет только на способ аутентификации и порт, но не на то, куда вы попадаете.


Приватный ключ — это и есть ваша личность для SSH. Любой, у кого есть копия приватного ключа, может выдать себя за вас: пушить в репозитории, к которым у вас есть доступ, переписывать историю, читать приватный код.

git remote -v
ssh -T git@github.com

Короткий error report: Permission denied (publickey)
Эта ошибка означает, что SSH-сервер GitHub отклонил аутентификацию: вы пытаетесь подключиться по SSH, но не предъявили ключ, который GitHub распознаёт


Что проверять первым при wrong URL или permission denied
При ошибке доступа первым делом проверяйте URL и аутентификацию, а не ветку или историю. Сначала git remote -v — убедитесь, что remote указывает туда, куда нужно, и в правильном формате (HTTPS или SSH соответственно вашему способу входа). Затем проверьте аутентификацию (ssh -T git@github.com для SSH или валидность токена для HTTPS). Причина проста: «permission denied» и «repository not found» — это ошибки транспорта и прав доступа; они возникают ещё до того, как Git вообще доберётся до содержимого репозитория. Имя ветки и история к ним отношения не имеют. Менять branch name бессмысленно — сервер ещё не дошёл до веток. А force push в такой ситуации особенно опасен: если URL случайно указывает на чужой или не тот репозиторий и доступ всё-таки сработает, форс-пуш может затереть чужую историю. Сначала чините адрес и доступ, и только потом думайте о ветках.
