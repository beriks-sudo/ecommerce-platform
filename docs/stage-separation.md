# Stage separation

## Что делает builder stage
builder — это «рабочая кухня». В ней есть Composer и инструменты сборки.
Тут ставятся зависимости (`composer install`) и готовятся файлы приложения в `/app`.
builder может быть «грязным» — в нём лежат инструменты, нужные только для подготовки.

## Что делает runtime stage
runtime — это «чистая витрина». Она начинается с PHP runtime image (`php:8.5-cli-alpine`).
В неё переносится только готовый результат из builder, задаётся рабочая папка и команда запуска.
В runtime нет Composer и инструментов сборки — только то, что нужно для запуска приложения.

## Почему COPY --from=builder отличается от COPY из context
Обычный `COPY` берёт файлы из build context (из проекта на диске).
`COPY --from=builder` берёт файлы из другой stage этого же Dockerfile (из результата builder).
Так финальный образ получает только готовый результат, без инструментов сборки.

## Что не должно оставаться в runtime image без причины
Composer, build tools, build cache, dev-зависимости и временные файлы.
Каждому из них нужен отдельный повод остаться. По умолчанию их в runtime быть не должно —
чем меньше лишнего, тем проще понять образ и искать ошибку.

## Зачем make build-builder полезен для диагностики
`make build-builder` собирает только builder stage (`docker build --target builder`).
Если build-builder проходит — значит build-зона собирается нормально.
Если после этого `make build` (runtime) падает, проблема ниже по Dockerfile:
в `COPY --from`, в отсутствующем файле, в runtime base image или в `CMD`.
Это сужает круг поиска вместо чтения всего build-лога одним потоком.
