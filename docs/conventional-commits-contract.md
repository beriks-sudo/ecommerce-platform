Commit message является интерфейсом между автором изменения и всеми будущими читателями истории. Автор знает контекст в момент работы, но история живет дольше его памяти. Хорошее сообщение отвечает минимум на два вопроса: какая область поведения изменилась и зачем это изменение существует. Conventional Commits добавляют к этому машинно читаемый префикс, но даже без автоматизации важна сама дисциплина. Когда команда договорилась, что fix означает исправление observable behavior, а feat означает новую возможность для пользователя или внешней системы, история становится полезной для release review. Такой контракт особенно важен после Module 05: если изменение проходит через protected branch, staging и release decision, commit message становится одним из сигналов для всего пути доставки.

type(scope): description

Good examples (5)
1. feat(cart): add coupon validation
   Полезно: ясный type (новая возможность), scope = область продукта (cart), description описывает результат через поведение. Release manager сразу видит — это feature для changelog.
2. fix(auth): keep session after password change
   Полезно: видно, что чинят observable behavior (сессия больше не сбрасывается). Reader понимает impact без открытия diff. Хороший кандидат для поиска при regression.
3. fix(checkout): reject empty delivery address
   Полезно: конкретное поведение, а не «исправил баг». Понятно, что именно теперь происходит. Легко найти при hotfix или backport.
4. docs(release): explain rollback checklist
   Полезно: type docs честно говорит, что это документация, scope уточняет — про release. Release manager знает, что в changelog для пользователей это можно не тащить.
5. feat(checkout)!: replace delivery slot response format
   Полезно: ! явно сигнализирует breaking change. Release manager обязан проверить SemVer impact (major) и migration notes. Сигнал не спрятан в теле.
   Bad examples (5)
1. update
   Вредно: непонятно ничего — логика, документация или конфиг? Нет type, нет scope, нет смысла. Reviewer вынужден читать весь diff.
2. fix
   Вредно: ясно только что «что-то починили». Нет области и нет поведения. Release manager не может собрать changelog, инженер не найдёт commit по смыслу.
3. feat: checkout
   Вредно: type есть, но description размытый — что именно появилось в checkout? Звучит как название области, а не результат.
4. fix(OrderController.php): change method
   Вредно: scope использован как имя файла, а не область продукта. Это не помогает найти контекст и завязывает сообщение на текущую структуру кода. Description тоже про действие, а не про поведение.
5. feat(db): alter column (с тихим breaking change)
   Вредно: слишком технически — говорит о действии с базой, но не про user-visible intent. Если это ломает совместимость, а ! и BREAKING CHANGE не указаны — release process не увидит major impact и выпустит неверную версию.
   Общий принцип на примерах: плохие сообщения описывают действие автора или файл, хорошие — намерение и поведение продукта.
   Связь с Module 05 (release flow)
   Conventional Commits работают как сигнал на каждом шаге пути доставки:

Review. Reviewer по type/scope сразу видит заявленный intent и проверяет его честность: правда ли fix — это исправление, а не спрятанный breaking change. В mature workflow PR title = squash commit message, поэтому он должен соответствовать формату так же строго.
CI. Простой формат легко проверять автоматически (commitlint, hook, правило в CI). CI распознаёт feat, fix, !, BREAKING CHANGE и может отклонить коммит с неверным форматом.
Release notes. Команда не копирует сырой git log, а группирует изменения по intent: features отдельно, fixes отдельно, breaking changes отдельно. Это возможно только если type честный.
Tag / SemVer. Type определяет version impact: fix → patch, feat → minor, !/BREAKING CHANGE → major. По истории видно, какой tag ставить.
Production / release branch. В release branch команда может разрешать только fix, docs, chore(release) и запрещать новые feat. Формат сообщения помогает enforce это правило.

Связь с Module 06 (hotfix, undo, backport, поиск)

Hotfix. При инциденте команда быстрее находит нужный commit по fix(payment): ..., понимает область и поведение без чтения patch — это экономит время, когда production лежит.
Safe undo. Чтобы безопасно откатить изменение, нужно точно понимать, что оно делало. Хорошее сообщение объясняет поведение, поэтому при revert/undo меньше риска снести не то.
Backport. По сообщению понятно, какой именно fix и какое user-visible поведение он чинит → легче решить, нужен ли он в support line и применим ли к старой версии. feat в support line обычно не тащат, и формат сразу это показывает.
Поиск нужного commit. Понятные сообщения превращают историю в искомую базу: можно отфильтровать по type/scope (fix(checkout)) и найти commit по смыслу, а не вычитывать каждый diff. Голые update/fix делают такой поиск невозможным.

Local Checks
Перед тем как опубликовать изменение, выполняй локальные проверки:
git diff --check
git status --short
make check
Зачем git status --short. Короткий статус показывает компактным списком, что именно попадёт в коммит: какие файлы изменены, добавлены, не отслеживаются. Это защищает от неатомарного коммита — то есть от ситуации, когда под сообщением fix(order): validate total лежат заодно правки UI, README и .gitignore. Conventional Commit честен только над атомарным изменением, поэтому сначала смотришь статус и убеждаешься, что в коммите ровно то, что описывает сообщение.
Зачем make check. Эта команда прогоняет проверки проекта (тесты, линтер) перед публикацией. Она не заменяет смысл сообщения, но фиксирует привычку: перед отправкой проверяется и рабочая копия (код рабочий), и история (сообщение честное). git diff --check дополнительно ловит мусор вроде whitespace-ошибок и конфликтных маркеров.
Итог: git status --short гарантирует, что коммит атомарный и сообщение ему соответствует, а make check — что отправляемый код проходит проверки. Вместе они держат тот самый контракт: сообщение в истории должно честно отражать проверенное изменение.
