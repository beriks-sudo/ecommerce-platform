Лимиты как guardrails, а не лечение

Resource limit — это граница ущерба, а не исправление причины.

Что лимит делает:
- не даёт одному сервису съесть весь host и обрушить соседей;
- делает проблему заметной (контейнер с утечкой раньше упрётся в потолок и упадёт по OOM).

Чего лимит НЕ делает:
- не чинит memory leak — утечка продолжит течь, просто упрётся в лимит раньше;
- не ускоряет медленный SQL — лимит CPU может даже замедлить запрос;
- не исправляет тяжёлый worker или плохую архитектуру.

Причина высокого потребления — в следующем слое (код, запрос, конфиг worker).
Порядок: наблюдай (stats/inspect) → локализуй слой → меняй config отдельным
коммитом через review. Удалять лимит, когда он поймал проблему, — значит убирать
сигнал вместо лечения.
