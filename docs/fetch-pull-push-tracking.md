  │  Команда  │               Направление                │ Меняет твою рабочую ветку? │
  ├───────────┼──────────────────────────────────────────┼────────────────────────────┤
  │ git fetch │ GitHub → ноут (только метаданные)        │ ❌ нет                     │
  ├───────────┼──────────────────────────────────────────┼────────────────────────────┤
  │ git pull  │ GitHub → ноут (с вливанием в твою ветку) │ ✅ да                      │
  ├───────────┼──────────────────────────────────────────┼────────────────────────────┤
  │ git push  │ ноут → GitHub                            │ ❌ на ноуте ничего         │
  └───────────┴──────────────────────────────────────────┴────────────────────────────┘

  git fetch — «разведка»
  
    Самая безопасная команда. Что делает:
  
    - сходила на GitHub
    - посмотрела, какие там новые коммиты на ветках
    - скачала их в твой .git (объекты есть, но они в стороне)
    - обновила «локальные пометки» о том, что сейчас на сервере — это origin/main, origin/feature и т.д.
  
    Что НЕ делает:
    - ❌ не меняет твои файлы в папке
    - ❌ не двигает твою текущую ветку
    - ❌ не создаёт merge-коммитов
  
    Аналогия: ты заглянул в почтовый ящик и увидел, что есть письма. Открывать и читать пока не обязательно.
  
    После fetch можно спокойно посмотреть, что прилетело:
    git fetch origin
    git log --oneline --graph --all -10
  
    Используй fetch всегда, когда хочешь просто понять, что на сервере, не трогая свою работу.
  
    ---
    git pull — «забрать и сразу влить в текущую ветку»
  
    Это fetch + автоматическое слияние новых коммитов в твою текущую ветку.
  
    То есть:
    1. Сходил на GitHub
    2. Скачал новые коммиты
    3. Тут же попытался влить их в твою ветку (через merge или rebase)
  
    В этом и подвох. Если у тебя в папке грязно (незакоммиченные правки) или ветка разошлась с remote, pull может:
    - создать merge-коммит
    - запустить rebase
    - остановиться на конфликте
  
    Правило безопасности перед pull:
    git status --short    # чисто? Если нет — сначала commit или stash
    git pull
  
    Аналогия: ты не просто заглянул в ящик, а вскрыл письма и сразу подшил их к своему текущему документу. Если документ не дописан — будет каша.
  
    ---
    git push — «отправить свои коммиты на GitHub»
  
    Идёт в обратную сторону: твои локальные коммиты → на remote.
  
    Важно:
    - ❌ незакоммиченные файлы не отправляются (push отправляет только commits!)
    - ❌ push не заменяет commit. Сначала git add + git commit, потом git push
    - ⚠️  сервер может отказать — и это часто нормально, не баг


remote branch -> fetch -> origin/<branch> -> pull -> local branch
local branch -> push -> remote branch

 git push -u origin my-branch

  -u (= --set-upstream) делает две вещи:
  1. Отправляет ветку на GitHub (если её там ещё нет — создаёт)
  2. Записывает в конфиг: «локальная my-branch ↔ origin/my-branch»

  После этого git push и git pull работают без аргументов — Git помнит связь.

 git branch -vv

  Пример:
  * my-branch  a1b2c3d [origin/my-branch: ahead 2]   feat: add cart
    main       226dc83 [origin/main]                  Initial commit

  Читать так:
  - * — текущая ветка
  - a1b2c3d — последний коммит
  - [origin/my-branch: ahead 2] — связана с origin/my-branch, у тебя на 2 коммита впереди (т.е. 2 ещё не запушены)
  - [origin/main] без слов — синхронно

  Важно: числа ahead/behind правдивы только после свежего git fetch. Это сравнение с последним известным состоянием remote, а не с настоящим — Git не ходит
  на сервер при каждом status.


Non-fast-forward кратко

  Что это

  git push отказал с сообщением:
  ! [rejected] my-branch -> my-branch (non-fast-forward)

  Перевод: «На сервере есть коммит, которого у тебя нет. Если я приму твой push — я его затру.»

  remote:   A — B — C — X        ← X появился, у тебя его нет
  у тебя:   A — B — C — D — E    ← push сюда снёс бы X

  Это защита, а не баг.

  Откуда X берётся

  - коллега запушил раньше
  - ты пушил с другого ноута
  - ты делал rebase локально и переписал свою же историю
  - старая remote-ветка от прошлой попытки

  Что делать — ВСЕГДА сначала это

  git fetch origin
  git log --oneline --graph --all -15
  git branch -vv

  Сначала смотрим, потом решаем. Никогда не --force первым шагом.

  Дерево решений

  ┌────────────────────────────────────┬─────────────────────────────────────┐
  │              Ситуация              │             Что делать              │
  ├────────────────────────────────────┼─────────────────────────────────────┤
  │ На remote чужой/нужный коммит      │ git pull --rebase → потом git push  │
  ├────────────────────────────────────┼─────────────────────────────────────┤
  │ Пушу не в ту ветку                 │ проверить git branch --show-current │
  ├────────────────────────────────────┼─────────────────────────────────────┤
  │ Своя личная ветка, мусор на remote │ git push --force-with-lease         │
  ├────────────────────────────────────┼─────────────────────────────────────┤
  │ Ветка main или protected           │ никакого force, только через PR     │
  └────────────────────────────────────┴─────────────────────────────────────┘

  Главное

  1. Не force first. Сначала fetch и анализ.
  2. --force-with-lease безопаснее --force — откажет, если кто-то успел запушить.
  3. На main force запрещён. Точка.
