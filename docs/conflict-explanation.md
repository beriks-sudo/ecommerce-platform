# Conflict explanation — Module 04, Lesson 5

## Что означают markers
В конфликтном файле Git записывает обе версии и помечает их служебными строками:

    marker: <<<<<<< HEAD                          — версия текущей ветки (target), куда вливаем
    marker: =======                               — separator между двумя версиями
    marker: >>>>>>> practice/conflict-incoming    — incoming side, версия вливаемой ветки

Префикс `marker:` стоит специально, чтобы `git diff --check` не принял этот
учебный пример за незакрытый конфликт.

## Почему возник conflict
Conflict был в docs/base-text.md.
Обе ветки независимо изменили одну и ту же строку базового текста: текущая
ветка (HEAD) записала туда "Базовый текст 3", а ветка
practice/conflict-incoming — "Базовый текст 2". Так как изменён один и тот же
участок, Git остановил автоматическое слияние: он не может решить за человека,
какое из значений верное, и не имеет права молча выбросить одно из них.

## Намерение каждой стороны
Обе ветки развивали один и тот же базовый текст параллельно, поэтому в одной
строке оказались две разные версии содержания.

- Текущая (HEAD): хранила формулировку "Базовый текст 3" — актуальное
  состояние target-ветки на момент merge.
- Incoming (practice/conflict-incoming): приносила формулировку "Базовый текст 2",
  отражающую изменение, сделанное в отдельной ветке.

Git остановился не потому, что одна из версий "неправильная", а потому что обе
стороны изменили одну строку, и автоматический выбор мог бы потерять
содержание одной из веток.

## Итоговое решение
Выбрано объединение обеих строк, чтобы не потерять содержание ни одной ветки:

    Базовый текст 2
    Базовый текст 3

Это решение сохраняет смысл обеих сторон: каждая внесённая версия остаётся
в файле как отдельная строка, ничего не затёрто. Если бы вместо этого был
применён accept current или accept incoming, одна из версий исчезла бы без следа.
Маркеры (<<<<<<<, =======, >>>>>>>) удалены, конфликтный блок не оставлен —
собран единый корректный файл.

## Почему нельзя механический accept all
Нажать "accept current" или "accept incoming" на все конфликты сразу опасно:

- accept current во всех местах молча выбрасывает все incoming-изменения —
  можно потерять чужую работу, миграцию или важную проверку.
- accept incoming во всех местах затирает собственные изменения текущей ветки.
- автоматический выбор не читает смысл задачи, поэтому может оставить
  логически несовместимый результат, который технически собирается, но
  ломает поведение.

Поэтому конфликт прочитан вручную, обе стороны сопоставлены по смыслу, и только
после этого собрана итоговая версия.

## Проверка после решения
    make check
    git status --short
    git diff --check

git diff --check дополнительно ловит оставшиеся conflict markers в diff.
