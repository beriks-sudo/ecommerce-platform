О чём вообще речь
Cherry-pick — это способ взять один конкретный коммит из одной ветки и применить его на другой ветке. Не сливать всю ветку, не переносить кучу изменений — только один patch.
Аналогия: представь, что у тебя есть feature-ветка с 10 коммитами, и среди них — один маленький bugfix. А в release-ветке нужен только этот фикс, остальное туда тащить нельзя (там незаконченная работа, эксперименты, всё подряд). Cherry-pick вырезает только нужный коммит.

Зачем это нужно — типичные ситуации

Backport — баг исправили в main (новая версия), но клиенты сидят на старой версии 1.7. Нужно перенести фикс в support/1.7 и выпустить patch-релиз.
Hotfix обратно в develop — починили прод в main, теперь надо вернуть этот фикс в develop, иначе при следующем релизе старый баг вернётся к пользователям (помнишь схему из прошлого урока с буквой H?).
Срочный фикс в замороженный release — release candidate уже заморожен, нельзя сливать всю ветку, но один blocking-fix нужен.

git status --short
git cherry-pick -x abc1234
# если конфликт
git status
# исправить файлы
git add docs/cherry-pick.md
git cherry-pick --continue
make check

18:06Claude responded: 1.1. Почему SHA нового коммита другой, но footer сохраняет связь
SHA считается от содержимого коммита + ссылки на parent. При cherry-pick parent уже другой (последний коммит target-ветки, а не исходной) → SHA автоматически другой. Это не баг, это математика хэширования: один и тот же коммит в двух местах истории иметь одинаковый SHA не может.
Флаг -x дописывает в message строку (cherry picked from commit abc1234). Это просто текст, человекочитаемая нитка между коммитами — для audit trail, поиска backport'ов и понимания, что это перенос, а не оригинал. Техническая связь потеряна, семантическая — сохранена.
Аналогия: тот же дом по чертежу, но на другой улице. Чертёж (diff) совпадает, адрес (SHA) другой, табличка «копия дома №5 с улицы А» (footer) сохраняет связь.

2. Конфликты при cherry-pick — короткий flow
   bashgit cherry-pick -x abc1234
# ── КОНФЛИКТ ──
git status                    # 1. понять, какие файлы конфликтуют
# 2. открыть файл, разобрать маркеры <<<<<<< ======= >>>>>>>, оставить правильный код
git add <файл>                # 3. пометить как исправленный
git cherry-pick --continue    # 4. завершить коммит
make check                    # 5. ОБЯЗАТЕЛЬНО проверить
Если понял, что переносишь не то/не туда:
bashgit cherry-pick --abort       # чистый откат до состояния «как было»
Главное: конфликт — это сигнал «контекст другой, прими решение», а не поломка. --abort — нормальный выход, если patch ветке не подходит.
