на commit. «Защищённость» обеспечивает платформа настройкой protected branch:

# main как доверенная линия — Module 04, Lesson 1

## Роль main
`main` — доверенная общая линия проекта, а не личное рабочее место. Команда
опирается на её состояние: от `main` синхронизируются другие разработчики, по
ней строится CI, от неё считается release candidate, а merge может запускать
production deploy. Поэтому в `main` попадает только проверенное состояние,
прошедшее review и checks. Обычная работа ведётся в отдельной feature branch
и вливается в `main` только через проверяемый путь.

## Gates: что защищает общую линию
Между feature branch и protected `main` стоит набор обязательных проверок
(gates). Каждый закрывает свой риск:

- **Local self-check (`make check`)** — дисциплина автора. Убирает очевидно
  сломанный diff ещё до PR, уменьшает шум для reviewer. Не заменяет review и
  branch protection: отвечает только за личную аккуратность.
- **Review** — проверка смысла человеком. Reviewer читает diff, проверяет
  intent, задаёт вопросы про риск, ищет потерянные edge cases и смотрит, не
  смешаны ли несколько задач в одном изменении.
- **CI** — повторяемая машинная проверка из чистого состояния (тесты, lint,
  build, project checks). Привязан к commit SHA / merge candidate: после нового
  push diff обновляется и checks запускаются заново.
- **Запрет direct push** — самый короткий путь (push прямо в `main`) закрыт.
  Платформа отклоняет обновление защищённого ref и направляет изменение через
  PR/MR.
- **Запрет force push** — нельзя переписать историю защищённой линии. Это не даёт
  потерять чужие commits и ломать общую точку отсчёта.
- **Ответственность maintainer / code owner** — право нажать merge принадлежит
  не любому, а maintainer, code owner или release owner. Так merge остаётся
  осознанным решением, а не случайным действием.

## Почему не работаем прямо в main
Git технически разрешает сделать commit в `main`, но в команде это ломает
доверие к общей линии. Цена ошибки для команды:

- от `main` синхронизируются другие разработчики — одна незавершённая правка
  наследуется во всех их ветках;
- review строит diff относительно `main` — сломанная база искажает все сравнения;
- CI собирает artifact и release process считает `main` кандидатом на production —
  все эти процессы начинают обслуживать случайное состояние одного человека.

Главная мысль: прямая работа в `main` превращает «состояние, которое случайно
получилось на одной машине» в состояние всей команды. Поэтому черновая работа
изолируется в feature branch, а `main` остаётся стабильной точкой отсчёта.

## Что считается ошибкой
Типичные нарушения выглядят почти безобидно, но обходят общую ответственность:

- **Direct push в main** — коммит сразу в защищённую линию мимо PR/MR. Изменение
  попадает к команде без review и CI.
- **Self-merge без review** — автор сам вливает свой PR без второго взгляда.
  Формально процесс есть, фактически diff никто не проверил.
- **Merge с красным CI** — «CI красный из-за flaky test, можно merge». В общую
  линию попадает изменение с непройденными проверками.
- **Обход checks фразой "у меня локально работает"** — зелёный local check
  объявляется заменой review и CI. Но локальная проверка отвечает только за
  автора, а не за общую линию из чистого состояния.

Срочность не отменяет правил: даже hotfix должен оставлять след — отдельная
ветка, укороченный emergency review, checks и понятный commit. Исключение не
должно становиться нормой.

## Как проверить перед отправкой
Перед открытием PR полезен self-review:

    make check
    git status --short

`make check` запускает проектные проверки и снижает вероятность отправить
очевидно сломанный diff. `git status --short` показывает незакоммиченный мусор
и подтверждает, что рабочее дерево чистое перед push.
