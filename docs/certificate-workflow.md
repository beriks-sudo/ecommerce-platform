# Certificate workflow

## Как генерировать dev-сертификаты

Локальные сертификаты создаёт скрипт `bin/generate-local-certs.sh` через `openssl`.
Запуск:

```bash
make local-certs
```

Скрипт кладёт два файла в `docker/traefik/certs/`:

- `localho.st.key` — приватный ключ;
- `localho.st.crt` — self-signed сертификат с SAN на `ecommerce.localho.st`
  и `*.ecommerce.localho.st`.

Процесс воспроизводим: любой участник команды клонирует репозиторий, запускает
`make local-certs` и получает свои локальные сертификаты. В Git попадает только
скрипт генерации, а не сами сертификаты.

## Trust (доверие)

Локальный сертификат — self-signed: его никто авторитетный (CA) не подписывал,
поэтому браузер его не знает и показывает предупреждение. Это нормально для dev.

Важно различать два разных слоя:

- **route** — Traefik довёл запрос до нужного сервиса (маршрут работает);
- **trust** — доверяет ли клиент сертификату.

Предупреждение в браузере означает проблему trust, а не сломанный route.
`curl -k` / `-kI` временно игнорирует проверку доверия — это только для
диагностики (проверить, что сервер отвечает по HTTPS), безопасным соединение
это не делает и в production не применяется.

## Почему private key нельзя хранить в Git

Приватный ключ — это секрет. Если закоммитить его, он попадёт в историю Git и
перестанет быть приватным: его увидит любой, у кого есть доступ к репозиторию.

- Production-ключи не коммитятся **никогда**.
- Локальные dev-ключи тоже не коммитим — они в `.gitignore`, команда
  воспроизводит их локально командой `make local-certs`.
- В Git хранится только workflow генерации и файл `.gitkeep`, чтобы пустая
  папка `docker/traefik/certs/` существовала в репозитории.
