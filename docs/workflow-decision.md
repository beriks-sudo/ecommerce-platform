# Decision matrix: какой Git-флоу выбрать

Логика та же, что в уроках: `develop`, `staging`, `release/*`, теги — это **слои с ценой**, а не обязательные ступени зрелости. Каждый слой вводят тогда, когда риск, который он закрывает, дороже его поддержки. Главный вопрос в каждой строке: *что мы платим и что за это получаем?*

---

## 1. Solo (один разработчик, пет-проект / pet-prod)

| Поле | Значение |
|---|---|
| **Recommended flow** | `protected main` (мягко) + короткие feature branches + tag на релиз. `develop` не нужен. |
| **Required gates** | Локальный `make check` перед push, CI с базовыми тестами/линтером на PR в main. |
| **Release cadence** | По готовности, в любой момент (continuous). |
| **Rollback cost** | Очень низкий: revert коммита или передеплой предыдущего tag. |
| **Why this is enough** | Нет параллельных команд, чьи изменения надо "встречать" до релиза. Integration line встречать нечего — автор и так видит всю картину. |
| **What would be too much** | `develop` + `staging` + `release/*` + QA sign-off. Это только тормозит одного человека и создаёт линии, которые некому поддерживать зелёными. |
| **Residual risk** | Нет внешнего ревью — баги ловит только автор и CI. Нет pre-prod проверки на проде-подобных данных: миграция или конфиг могут сломаться уже у пользователей. |

---

## 2. Small team (2–6 человек, быстрый CI, частые релизы)

| Поле | Значение |
|---|---|
| **Recommended flow** | **Trunk-based**: `protected main` + короткоживущие feature branches + tag. `develop` обычно избыточен. |
| **Required gates** | PR с обязательным review (хотя бы 1 reviewer), зелёный CI, `make check` локально, запрет direct push в main. |
| **Release cadence** | Часто: ежедневно или несколько раз в неделю. |
| **Rollback cost** | Низкий: revert + быстрый передеплой, дешёвый откат на предыдущий tag. |
| **Why this is enough** | Ветки живут недолго, конфликты приходят рано, CI быстрый. Задержка от отдельной integration line больше, чем риск смешать непроверенное. |
| **What would be too much** | Полноценный `develop` + `release/*` + ручной staging-цикл. Команда заплатит за слой, но раннюю интеграцию почти не получит — она и так происходит в main. |
| **Residual risk** | Нет буфера между merge и production — плохой PR быстро доезжает до пользователей. Минимальная pre-prod проверка: то, что зелено в CI, не значит, что продуктовый сценарий рабочий. |

---

## 3. SaaS (растущий продукт, несколько фич параллельно, единый прод)

| Поле | Значение |
|---|---|
| **Recommended flow** | `develop` (integration line) → `staging` candidate → `main`/tag в production. Опционально `release/*` под крупные версии. |
| **Required gates** | PR + review в `develop`, integration checks, деплой кандидата на staging, smoke + ключевые QA-сценарии, release decision перед production. |
| **Release cadence** | Регулярно: еженедельно / по спринтам, плюс возможность hotfix вне очереди. |
| **Rollback cost** | Средний: откат на предыдущий tag + внимание к миграциям БД (не всякую миграцию легко откатить). |
| **Why this is enough** | Несколько связанных задач идут параллельно — нужна точка, где их совместное поведение видно до прода. Staging ловит то, что не виден в одиночном PR (конфиг, миграции, интеграции). |
| **What would be too much** | Тяжёлый regulated-процесс: формальный sign-off с подписями, длинные scheduled windows, отдельные release-ветки на каждый мелкий фикс. Это убьёт скорость SaaS без пропорциональной выгоды. |
| **Residual risk** | Staging ≠ production (данные, масштаб, sandbox-интеграции отличаются) — часть багов проявится только на проде. Риск рассинхрона: hotfix попал в main, но не вернулся в `develop`, и следующий релиз вернёт старый баг. |

---

## 4. Enterprise (большая команда, QA-цикл, release windows, поддержка версий)

| Поле | Значение |
|---|---|
| **Recommended flow** | `develop` → `release/X.Y` (стабилизация, заморозка scope) → `main` + immutable artifact из tagged commit → production. Backport hotfix обратно в `develop`. |
| **Required gates** | PR + review + owner на каждой линии, integration checks в develop, regression на staging, QA sign-off, migration plan, rollback plan, release notes. |
| **Release cadence** | Окнами: запланированные релизы (раз в спринт/месяц), поддержка нескольких версий одновременно. |
| **Rollback cost** | Высокий: координация, откат artifact из tagged commit, откат/совместимость миграций, оповещение клиентов. |
| **Why this is enough** | Много людей, параллельные фичи, scheduled releases и поддержка старых версий требуют слоя стабилизации, где scope заморожен, а разработка следующего продолжается в develop. |
| **What would be too much** | Полный compliance-overhead (внешний аудит каждого изменения, формальная валидация под регуляторов). Для не-regulated продукта это бюрократия без снижения реального риска. |
| **Residual risk** | Сложность процесса повышает шанс человеческой ошибки в синхронизации линий (потерянный backport). Длинные release-ветки рискуют стать "вторым develop", если в них протаскивают фичи. |

---

## 5. Regulated (финтех, медицина, госсектор — высокая цена инцидента и аудит)

| Поле | Значение |
|---|---|
| **Recommended flow** | `develop` → `release/X.Y` → подписанный tag → immutable verified artifact → production, с **полной traceability** каждого перехода. Hotfix только через release/hotfix-линию с обязательным backport. |
| **Required gates** | Всё из enterprise + обязательный формальный sign-off (QA + security + compliance), audit trail (кто, что, когда, какой commit/artifact), запрет ручных правок на сервере, контролируемые доступы и секреты, проверка миграций на prod-like данных. |
| **Release cadence** | Редко и строго по окнам: контролируемые релизы с заранее согласованным scope и change-approval. |
| **Rollback cost** | Очень высокий: откат + документирование инцидента + возможные регуляторные последствия и отчётность. |
| **Why this is enough** | Цена production-инцидента (деньги, здоровье, юридическая ответственность) оправдывает каждый слой проверки и полную воспроизводимость: на вопрос "какой commit/artifact/config работал у пользователей" должен быть точный ответ. |
| **What would be too much** | Здесь почти нет "слишком много" в части контроля — избыточным становится разве что хаотичное добавление процессов без owner и без автоматизации, что превращает контроль в неподдерживаемую бюрократию. |
| **Residual risk** | Скорость поставки низкая — срочные фиксы проходят медленнее, чем хотелось бы. Тяжесть процесса сама становится риском: люди ищут обходные пути, если gates неудобны, что подрывает аудит. |

## Как читать матрицу

Сверху вниз растут две вещи одновременно: **цена инцидента** и **цена процесса**. Идея уроков — держать их сбалансированными. Слой (`develop`, `staging`, `release/*`, формальный sign-off) оправдан только когда:

```
риск, который он закрывает  >  цена его поддержки
```

И сквозной принцип из урока 3: на каждом уровне ветка ≠ среда. Чем правее по этой таблице, тем критичнее точная речь — не "production это main", а "commit f2a9c10 / artifact app:v1.8.0 / environment production".

---

## Два опорных flow

Эти два варианта — крайние точки спектра. Всё остальное в матрице находится между ними.

### Flow A — лёгкий (trunk-based)

Подходит для solo и small team. Закрывает риск «один сломанный коммит у пользователей», но почти не платит за слои.

```text
short feature branch -> PR -> protected main -> deploy/tag
```

Что обязательно даже в самом лёгком виде: PR (а не direct push), зелёный CI, ветки живут коротко. Integration line отсутствует — её роль выполняет сам main, потому что встречать параллельные потоки почти нечего.

### Flow B — тяжёлый (integration + stabilization)

Подходит для enterprise и regulated, частично для зрелого SaaS. Платит за каждый слой и за это получает раннюю интеграцию, pre-prod проверку и воспроизводимый релиз.

```text
feature/* -> review -> develop -> staging -> release/* -> main -> tag -> production
```

Каждая стрелка — это граница ответственности из уроков:
- `feature/* -> review -> develop` — изменение принято в **интеграцию**, но ещё не в релиз.
- `develop -> staging` — собран конкретный candidate, проверяется в prod-like условиях.
- `staging -> release/*` — scope заморожен, идёт стабилизация версии.
- `release/* -> main -> tag` — релиз зафиксирован как **повторяемый факт** (tag, а не движущаяся ветка).
- `tag -> production` — в среде запущен immutable artifact из tagged commit.

## Decision note: что выбрать для учебного `ecommerce-platform` сейчас

Для учебного `ecommerce-platform` на текущем этапе я бы выбрал **Flow A — trunk-based**: короткие feature branches, PR с обязательным review, зелёный CI, protected main и tag на релиз. Причина в том, что цена ошибки сейчас учебная: нет реальных пользователей, чьи деньги или данные пострадают от бага, а значит тяжёлые слои закрывали бы риск, которого пока нет. Integration line `develop` здесь встречать нечего — параллельных связанных потоков почти нет, и одиночный PR показывает совместное поведение не хуже отдельной линии. Staging и `release/*` потребовали бы owner, который держит их зелёными, а в учебном проекте этот человек обычно отсутствует, и линии быстро превратились бы в «ветку с хаосом» из урока 1. Зато trunk-based приучает к правильным базовым привычкам: atomic commits, короткие ветки, self-review через `make check`, осмысленное PR-описание и tag как точка релиза. Это ровно та локальная дисциплина, без которой любой тяжёлый flow всё равно деградирует.

Перейти к более тяжёлому **Flow B** стоит, когда появятся конкретные триггеры, а не «для солидности». Первый сигнал — рост команды и параллельных фич: когда несколько человек одновременно меняют каталог, корзину и оплату, появляется реальная потребность встречать их изменения в `develop` до релиза. Второй — появление настоящих пользователей и платежей, из-за чего цена инцидента и стоимость rollback резко растут, и нужен `staging` для проверки миграций и payment sandbox в prod-like условиях. Третий — необходимость поддерживать выпущенные версии и релизить окнами, что требует `release/*` для заморозки scope и tagged artifact для воспроизводимости. Если со временем добавятся регуляторные требования (платёжный compliance, аудит), то поверх Flow B придут формальный sign-off и audit trail. Иными словами, flow должен догонять реальный риск, а не опережать его.

## Проверка решения

Прежде чем зафиксировать flow, ответь на эти вопросы. Если ответы тянут вправо по матрице — пора усложнять; если влево — выбранный тяжёлый flow избыточен.

**Team size.** Сколько человек одновременно меняют связанные части продукта? Один-двое — trunk-based. Много параллельных связанных потоков — нужна integration line `develop`.

**CI maturity.** Насколько надёжен и быстр CI? Быстрый и стабильный CI делает trunk-based безопасным. Если CI медленный или flaky, отдельные линии не спасут — сначала чините CI, иначе любой flow будет тормозить.

**QA.** Есть ли отдельный QA-цикл и ручная приёмка? Если да и она обязательна перед релизом — нужен `staging` с фиксацией commit/artifact/checks. Если проверки сводятся к зелёному CI — отдельная среда пока избыточна.

**Rollback cost.** Насколько дорого откатить релиз? Дёшево (revert + передеплой tag) — лёгкий flow допустим. Дорого (координация, необратимые миграции, оповещение клиентов) — нужен слой стабилизации и tagged artifact для предсказуемого отката.

**Support old versions.** Нужно ли поддерживать несколько выпущенных версий одновременно? Если да — почти неизбежны `release/*` и backport, иначе фиксы будут теряться между линиями.

**Regulatory needs.** Есть ли требования аудита, подписей, контролируемых доступов? Если да — поверх тяжёлого flow обязательны sign-off и audit trail с полной traceability; ручные правки на сервере запрещены.

**Ownership.** Есть ли конкретный человек/роль, отвечающий за каждую вводимую линию и среду — кто держит её зелёной, синхронизирует hotfixes, чинит broken state? Если owner нет, **не вводи слой**: без владельца `develop` или `staging` становятся дорогой витриной и источником хаоса, а не защитой.
