# Хорошее сообщение commit

Сообщение commit — это не формальность и не подпись для Git. Это короткое
объяснение для будущего читателя: для тебя через месяц, для reviewer на
pull request, для коллеги, который ищет, когда сломалось окружение. Если
сообщение слабое, история превращается в шум, и придется открывать каждый
diff, чтобы понять, что вообще произошло.

## Почему `fix`, `update`, `misc` плохо помогают команде

Эти сообщения не отвечают ни на один полезный вопрос. `fix` не говорит, что
именно было сломано. `update` не говорит, что обновилось и зачем. `misc`
прямо заявляет: автор сам не знает или не хочет формулировать.

Конкретные проблемы:

- **`git log` становится бесполезным.** Десять подряд `fix` и `update`
  выглядят одинаково. Найти нужный commit через `git log --oneline` или
  `git log --grep` невозможно.
- **`git blame` теряет смысл.** Когда находишь автора строки, ожидаешь
  объяснение. Видишь `update` — и идешь спрашивать в чат то, что должно
  было быть написано в сообщении.
- **Reviewer тратит время.** Вместо того чтобы прочитать сообщение и сразу
  понять контекст diff, он открывает каждый файл и пытается восстановить
  намерение автора.
- **Откат становится опасным.** Если нужно откатить плохой commit, по
  сообщению `fix` невозможно понять, что именно ты откатываешь и какие
  побочные эффекты будут.

## Три плохих сообщения и улучшенный вариант

### 1. `fix`

**Плохо:** `fix`

Не понятно: что сломалось, где сломалось, как починили.

**Лучше:** `Fix empty cart total when discount code is removed`

Теперь видно симптом (empty cart total), условие (when discount code is
removed) и направление работы (fix). Reviewer сразу знает, что искать в diff.

### 2. `update README`

**Плохо:** `update README`

Имя файла есть, смысла нет. README большой, и "обновил README" не говорит,
что именно изменилось: исправили опечатку, добавили раздел про установку,
переписали примеры команд?

**Лучше:** `Add make check section to README setup guide`

Понятно, какой раздел затронут и что в нем появилось. Если позже кто-то
будет искать, когда появилось упоминание `make check`, он найдет этот
commit за секунды.

### 3. `misc changes`

**Плохо:** `misc changes`

Худший вариант: автор честно признался, что в одном commit лежат разные
темы. Это сразу две проблемы: непонятное сообщение и плохая граница commit.

**Лучше:** разделить на два commit с осмысленными сообщениями:

```
Add notes on staged diff workflow
Fix typo in Makefile help target
```

Если темы две, commit тоже должно быть два. `misc` — это сигнал, что
staging собран неправильно, и пересобирать нужно его, а не сообщение.

## Сообщение отражает смысл, а не имя файла

`update config.php` — это сообщение про файл. `Increase session timeout to
30 minutes` — это сообщение про смысл. Имя файла видно в diff, его
повторять в сообщении бессмысленно. Сообщение должно отвечать на вопрос
"зачем", а не "где".

Это особенно важно, когда commit затрагивает несколько файлов одной темы.
Если ты изменил миграцию, модель и контроллер ради одной фичи, сообщение
`update User.php and UserController.php and migration` ничего не говорит.
А `Add email verification to user registration` объясняет всю группу
изменений одной фразой.

Правило простое: представь, что reviewer прочитал только сообщение и не
открывал diff. Если по сообщению он уже понимает, что произошло и зачем —
сообщение хорошее.

## Мост к Conventional Commits

Позже в курсе появится формат Conventional Commits: `feat:`, `fix:`,
`docs:`, `refactor:` и так далее. Тип станет формальным контрактом, и
сообщение будет выглядеть так:

```
docs: add notes on good commit messages
feat: add email verification to user registration
fix: handle empty cart total when discount is removed
```

Но это надстройка. Сначала нужно научиться писать содержательную часть —
ту, что идет после двоеточия. Если ты уже пишешь `Add notes on good commit
messages` вместо `update`, переход на `docs: add notes on good commit
messages` будет естественным. Если ты пишешь `fix`, никакой префикс не
спасет: получится `fix: fix`, и проблема останется той же.

Сейчас задача — научиться формулировать смысл. Формат придет следом.
