Представь, ты пишешь курсовую (feature branch). Стол завален черновиками, открытыми книгами, пометками. И тут научрук говорит: «срочно поправь опечатку в
  прошлой главе» (hotfix).

  Без worktree: убираешь всё со стола → достаёшь старую главу → правишь → возвращаешь черновики обратно. Долго и легко что-то потерять.

  С worktree: берёшь второй стол рядом. На нём раскладываешь старую главу, правишь, кладёшь обратно. Первый стол с черновиками не трогал вообще.

  Оба стола — твои, бумаги общие (из одного шкафа = из одного репозитория), но рабочие места разные.
  git worktree remove ../ecommerce-platform-hotfix
  git worktree list

  git clone создаёт полностью независимую копию репозитория: свои objects, своя .git папка, свой набор remote-связей. Два clone не знают друг о друге —
    ▎ коммит в одном не виден в другом, пока не сделать fetch/push через remote.
    ▎
    ▎ git worktree add создаёт дополнительную рабочую папку того же самого репозитория. Git objects (история, blobs, trees) переиспользуются через общий
    ▎ storage основного репозитория. В linked worktree вместо полноценной .git/ лежит маленький файл .git, который ссылается на основной репозиторий. Коммит,
    ▎ сделанный в linked worktree, сразу виден в основной папке — это одна и та же история.
    ▎
    ▎ Практическое следствие: clone дублирует диск и историю, worktree — нет. Зато worktree запрещает открывать одну ветку в двух папках одновременно (clone —
    ▎  пожалуйста, это разные репозитории).

  2. Checklist проверки каждой рабочей папки
  
    Текст для заметок:
  
    ▎ Перед работой в любой папке (основной или linked worktree) пробегай минимальный checklist:
    ▎
    ▎ pwd                          # где я физически нахожусь
    ▎ git branch --show-current    # какая ветка активна именно здесь
    ▎ git status --short           # что не закоммичено в этой папке
    ▎ make check                   # договор проекта прошёл в этом контексте
    ▎
    ▎ Дополнительно полезно: git worktree list — показывает карту всех связанных папок и какие ветки в них открыты.
    ▎
    ▎ Каждая команда отвечает на свой вопрос. Не пропускать ни одну — именно на пропуске одной из них и возникают ошибки уровня «я думал, я в hotfix, а я в
    ▎ feature».

    3. Почему clean status в одной папке не доказывает clean status в другой
  
    Текст для заметок:
  
    ▎ Linked worktree разделяет с основным репозиторием только Git objects (историю коммитов и содержимое файлов в этой истории). Но working tree (реальные
    ▎ файлы на диске) и index (staged-изменения) у каждого worktree свои.
    ▎
    ▎ Это означает:
    ▎ - git status --short в основной папке показывает изменения только основной папки.
    ▎ - В linked worktree рядом могут лежать незакоммиченные правки, конфликты после merge, файлы в index — основная папка о них ничего не знает.
    ▎ - make check, запущенный в основной папке, проверяет код в этой папке, а не код в hotfix-worktree.
    ▎
    ▎ Правило: чистоту и тесты нужно проверять там, где реально лежит работа. Перешёл в другой worktree — повтори checklist полностью.

    4. Предупреждение про feature branch → review → main
  
    Текст для заметок (можно оформить как ⚠️  блок):
  
    ▎ ⚠️  Локальная проверка ≠ право мержить в main.
    ▎
    ▎ Зелёный make check и чистый git status в feature branch означают только одно: ветка готова идти на review. Дальше она проходит через Pull Request: code
    ▎ review коллег, CI, обязательные проверки protected branch.
    ▎
    ▎ Никогда не пушить feature branch напрямую в main. main — protected branch: туда попадают только изменения, прошедшие review и CI. Worktree упрощает
    ▎ работу с несколькими ветками, но не отменяет branch discipline: review, CI, protected branches продолжают действовать так же, как и без worktree.
