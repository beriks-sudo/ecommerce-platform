Атомарные commits — заметка перед первым review
Что это
Атомарный commit — это одно законченное изменение, которое описывается одной фразой без слова "и". Если в message хочется написать "сделал X и поправил Y" — это два commit'а.
Проверка простая: можно ли откатить commit и получить рабочий проект? Если да — атомарный.
Это не про количество файлов
Одна мысль часто живёт в нескольких файлах. Например, добавляешь поле discount к товару:

models/Product.js — само поле
migrations/add_discount.sql — миграция
tests/product.test.js — тест

Это один commit, потому что по отдельности части не работают.
И наоборот: в одном файле могут быть две разные мысли (фикс + рефакторинг рядом) — это два commit'а.
Граница проходит по причине изменения, а не по файлам.
Почему смешанный commit дороже проверять
Reviewer вынужден:

сам мысленно делить diff на части,
держать в голове несколько контекстов сразу,
блокировать весь commit, если сомневается в одной части,
при поиске бага через месяц перечитывать всё, чтобы понять, что именно сломало.

Атомарные commits переносят работу с reviewer'а на автора — а автору это дешевле, он один помнит замысел.
Пример хорошего commit
feat(cart): валидация количества для товаров не в наличии

Если пользователь добавляет больше, чем есть на складе,
показываем ошибку и блокируем отправку. Проверка
на клиенте и на сервере.
Одна мысль, несколько файлов, message объясняет зачем.
Пример плохого commit
update stuff
А внутри:

валидация корзины,
фикс опечатки на кнопке оплаты,
переименование formatPrice → formatMoney,
обновление lodash,
новая секция в README.

Пять не связанных между собой причин. Reviewer не может одобрить часть. Через месяц git blame приведёт сюда с сообщением "update stuff" — и придётся читать весь diff.
Привычка перед commit
20 секунд, которые ловят большинство проблем:
bashgit status         # что вообще затронуто
git diff           # что изменено
git diff --staged  # что попадёт в commit
Если в --staged видишь больше одной мысли — раздели через git add -p.
